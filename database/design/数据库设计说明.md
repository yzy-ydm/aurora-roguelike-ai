## 1. 设计目标

### 1.1 核心目标

本数据库设计旨在为"基于云端AI动态内容生成的Roguelike游戏系统"提供可靠的数据持久化支持，主要目标包括：

1. **用户管理**：安全存储用户账号信息，支持注册、登录、权限管理
2. **游戏数据存储**：完整记录玩家角色状态、游戏进度、背包物品
3. **游戏内容管理**：存储武器、怪物、事件、地图等游戏核心数据
4. **AI生成记录**：记录所有AI动态内容生成的过程和结果，支持质量评估
5. **数据分析支持**：为后续数据分析和系统优化提供数据基础

### 1.2 设计原则

| 原则 | 说明 |
|------|------|
| **规范化** | 遵循第三范式（3NF），减少数据冗余 |
| **完整性** | 通过外键约束保证数据引用完整性 |
| **可扩展性** | 预留扩展字段，支持未来功能添加 |
| **性能优化** | 合理设计索引，优化常用查询 |
| **安全性** | 敏感数据加密存储（如密码） |

## 3. 数据表详细说明

### 3.1 users - 用户账号表

**用途**：存储系统用户的基本账号信息，用于身份认证和用户管理。

**字段说明**：

| 字段名 | 类型 | 必填 | 默认值 | 说明 |
|--------|------|------|--------|------|
| `id` | INT | 是 | 自增 | 主键，用户唯一标识 |
| `username` | VARCHAR(50) | 是 | - | 用户名，用于登录，唯一 |
| `password_hash` | VARCHAR(255) | 是 | - | 密码哈希值（bcrypt加密） |
| `email` | VARCHAR(100) | 否 | - | 邮箱地址，唯一 |
| `is_active` | TINYINT(1) | 否 | 1 | 账号状态：0-禁用，1-启用 |
| `last_login_at` | DATETIME | 否 | NULL | 最后登录时间 |
| `created_at` | DATETIME | 否 | CURRENT_TIMESTAMP | 记录创建时间 |
| `updated_at` | DATETIME | 否 | 自动更新 | 记录最后更新时间 |
| `is_deleted` | TINYINT(1) | 否 | 0 | 软删除标记：0-正常，1-已删除 |

**业务规则**：
- 用户名长度：3-50字符
- 密码使用bcrypt算法加密存储
- 支持软删除，不物理删除用户数据

### 3.2 player_profiles - 玩家角色信息表

**用途**：存储玩家的游戏角色属性、状态和统计数据。

**字段说明**：

| 字段名 | 类型 | 必填 | 默认值 | 说明 |
|--------|------|------|--------|------|
| `id` | INT | 是 | 自增 | 主键，档案唯一标识 |
| `user_id` | INT | 是 | - | 外键，关联users表 |
| `nickname` | VARCHAR(50) | 是 | - | 角色昵称 |
| `level` | INT | 否 | 1 | 角色等级 |
| `experience` | INT | 否 | 0 | 当前经验值 |
| `experience_to_next_level` | INT | 否 | 100 | 升级所需经验 |
| `max_health` | INT | 否 | 100 | 最大生命值 |
| `current_health` | INT | 否 | 100 | 当前生命值 |
| `attack` | INT | 否 | 10 | 基础攻击力 |
| `defense` | INT | 否 | 5 | 基础防御力 |
| `crit_rate` | DECIMAL(5,2) | 否 | 5.00 | 暴击率（%） |
| `gold` | INT | 否 | 0 | 金币数量 |
| `total_play_time` | INT | 否 | 0 | 总游戏时长（秒） |

## 4. ER关系说明

### 4.1 实体关系图

```

│                              Aurora Game Database ER图                           │

     │ PK id        │           │ PK id             │

     │ save_name    │           │ content_type      │
     │ player_state │           │ prompt, response  │
     └──────────────┘           └────────┬─────────┘
                                         │
                           ┌─────────────┼─────────────┐
                           │ 1:N         │ 1:N         │ 1:N
                           ▼             ▼             ▼
                    ┌──────────┐  ┌──────────┐  ┌──────────┐
                    │ weapons  │  │ monsters │  │  events  │
                    │──────────│  │──────────│  │──────────│
                    │ PK id    │  │ PK id    │  │ PK id    │
                    │ name     │  │ name     │  │ name     │
                    │ attack   │  │ health   │  │ type     │
                    │ rarity   │  │ attack   │  │ effect   │
                    └──────────┘  └──────────┘  └──────────┘
```

### 4.2 关系详细说明

| 关系 | 类型 | 说明 |
|------|------|------|
| users → player_profiles | 1:1 | 每个用户对应一个角色档案 |
| users → game_saves | 1:N | 每个用户可以有多个游戏存档（最多3个） |
| users → ai_generations | 1:N | 每个用户可以触发多次AI生成 |
| ai_generations → weapons | 1:N | 一次AI生成可以产生多个武器数据 |
| ai_generations → monsters | 1:N | 一次AI生成可以产生多个怪物数据 |
| ai_generations → events | 1:N | 一次AI生成可以产生多个事件数据 |
| ai_generations → maps | 1:N | 一次AI生成可以产生多个地图数据 |
| game_saves → ai_generations | 1:N | 一个存档可以关联多个AI生成记录 |

### 4.3 外键约束策略

| 外键 | 删除策略 | 说明 |
|------|----------|------|
| player_profiles.user_id | CASCADE | 用户删除时，角色档案一并删除 |
| game_saves.user_id | CASCADE | 用户删除时，游戏存档一并删除 |
| ai_generations.user_id | SET NULL | 用户删除时，保留AI记录但置空用户ID |
| weapons.ai_generation_id | SET NULL | AI记录删除时，保留武器数据 |
| monsters.ai_generation_id | SET NULL | AI记录删除时，保留怪物数据 |
| events.ai_generation_id | SET NULL | AI记录删除时，保留事件数据 |

## 6. 数据完整性约束

### 6.1 实体完整性

- 所有表都有主键约束
- 主键使用自增INT类型

### 6.2 参照完整性

- 使用外键约束保证关联数据的有效性
- 设置合理的删除策略（CASCADE/SET NULL）

### 6.3 域完整性

- 使用ENUM类型限制字段取值范围
- 使用NOT NULL约束保证必填字段
- 设置合理的默认值

### 6.4 用户定义完整性

- UNIQUE约束保证用户名、邮箱唯一性
- 复合唯一约束保证存档槽位唯一性

## 7. 设计决策说明

### 7.1 为什么使用JSON字段？

在以下场景中使用JSON字段存储数据：

1. **游戏状态数据**（player_state, inventory_data）
   - 游戏状态结构复杂且可能频繁变化
   - JSON提供灵活性，避免频繁修改表结构
   - 便于客户端序列化/反序列化

2. **AI生成的结构化数据**（parsed_data）
   - AI返回的数据结构可能不固定
   - JSON便于存储和后续解析

3. **地图配置数据**（room_data, monster_spawn_config）
   - 地图配置是复杂的嵌套结构
   - JSON更适合存储树形数据

### 7.2 为什么使用软删除？

用户表（users）采用软删除策略：

- 保留用户历史数据和关联记录
- 避免级联删除导致数据丢失
- 支持账号恢复功能

### 7.3 为什么记录AI生成历史？

专门设计ai_generations表的原因：

1. **可追溯性**：记录每次AI生成的输入输出
2. **质量评估**：支持用户评分和反馈
3. **数据分析**：分析AI生成内容的质量和效果
4. **成本控制**：记录Token使用量，监控API成本
5. **调试支持**：出现问题时可追溯原始数据

### 7.4 枚举类型的选择

使用ENUM类型而非单独的字典表：

- 简化查询，减少JOIN操作
- 数据值固定且有限
- 提高数据可读性
- MySQL ENUM类型存储效率高
